# 财报恢复与发布保护

这是数据可靠性保护，不是新的选股因子。基本面50/月线20/周线30、A/B路线、月J、周MA55、Top10累计、忽略设置和持仓做T要求保持原样。不承诺第三方数据源永不故障，也不通过填零、旧值或降低门槛凑满20只。

## 自动处理流程

1. 主财报、利润表、现金流表沿用原数据源与报告期/公告时点/版本匹配/TTM检查。每个分页须有一致的页数、声明总量和实际记录，无空页、重复或跨页重叠。
2. 分页不一致时，只清除此查询的页缓存，整组重新获取一次。普通传输故障仍保留成功页，只修缺页。
3. 在逐股技术扫描之前，检查未完成批次、财报质量匹配覆盖、扣非/现金流当前/TTM/同比输入覆盖，以及相对干净历史报告的骤降。只补取受影响财报批次；不为此再次请求全市场股票行情。
4. 补取同时绕过整表与分页缓存，并更新原缓存键，后续请求可以复用修复结果。损坏缓存重新获取；失败的新请求不保留旧响应冒充成功。
5. 最多补取2轮、并发2、总补取预算180秒，子进程受剩余预算限制。持续失败或预算耗尽保留缺失，不能无限等待。初次正常加载、已有Provider内部请求重试、数据解析/清理不包含在该额外补取预算内。

所有尝试及其真实状态保存在报告的`financial_integrity.collection.batches`，并单独输出附件`financial-integrity.json`。`successful_refetch_batch_count`只说明重新取得了响应，不等于财务质量已完整；最终以`status`和`alerts`为准。

## 可配置的保护阈值

`financial-integrity-config.json`独立于选股配置：

| 配置 | 默认值 | 含义 |
| --- | ---: | --- |
| retry_passes | 2 | 初次加载后的定向补取轮数上限 |
| workers | 2 | 补取并发上限 |
| retry_budget_seconds | 180 | 整体额外补取预算 |
| minimum_quality_coverage | 0.90 | 质量匹配及关键扣非/现金流输入覆盖保护线 |
| minimum_reference_coverage | 0.95 | 历史参考报告最低财报质量覆盖 |
| coverage_drop_percentage_points | 5 | 相对干净参考的覆盖降幅告警线（百分点） |
| batch_count_drop_fraction | 0.05 | 同报告期批次行数减少的重取/告警线 |
| reference_max_age_days | 14 | 参考报告最多相隔的自然日 |

这些是可审查的工程告警线，不是回测最优参数，不进入投资评分。配置校验限制并发、轮数和预算，不能用巨大重试数拖死工作流；不能将最低覆盖保护线设到80%以下。自定义配置可传`--financial-integrity-config`，历史目录可传`--financial-reference-directory`。

## 历史参照不参与填补财报

只选择此前正式收盘、日期一致、财报质量覆盖足够、无财报批次错误且没有被新保护标为degraded的报告。未来、同日、自相矛盾、过旧和故障报告被排除。使用覆盖比例适应报价股票数量的小幅变化。

历史报告只提供对比计数和明确带日期的阅读链接，不提供本次价格、财报数值、分数或候选替代值。没有可靠参照时仍执行绝对覆盖与失败批次保护。

10月28日只读回放选择**10月26日**作为干净参考：10月27日虽有5575只财报质量可用，其主财报`2026-09-30`批次仍有错误，不能据此把故障当成正常。

## 三种结果与强制发布检查

| 财报状态 | 报告呈现 | 完整性 |
| --- | --- | --- |
| healthy | 财报保护检查通过；真实合格股少于20也如实显示 | 不代表其他行情、B证据或估值也全部齐全 |
| limited | 顶部“评分数据待齐：部分入口股未参与排名”，单列股票及缺失字段 | 必须partial、scan_complete=false、ranking_complete=false |
| degraded | 顶部“财报数据异常：本次仅为诊断与已核验部分”，列出原因及带日期的干净历史参照 | 必须partial；禁止解释为全市场只剩几只合格股 |

`audit.py`与`publish.py`都执行保护校验：检查实际覆盖计数、批次记录、失败原因、强制刷新记录、历史参照、入口/待齐数量和中文提示。新报告保护标记丢失、状态伪装成healthy/complete、计数不符或提示被移除时，发布被拒绝。旧历史报告沿用原契约，不重写旧排名或Top10记录。

真实扫描工作流另有GitHub警告注解；扫描状态页也会注明财报异常。机器数据`financial_integrity`与中文报告同时发布，原`candidate_count`仍为真实全部入口股数。TOP20没有数据的股票不能被填入，也不会因此自动改变原资格或授予交易权限。

## 可复现验证

```bash
python -m pytest -q
node --test web-report/tests/*.test.mjs
python -m tommy_capital.financial_integrity --replay-summary results/2026-10-28/closing-summary.json
```

第三条命令只读真实归档，输出到`reports/financial-guard-replay/`，禁止写入正式results。可重现“入口9只、评分齐全2只、待齐7只”，识别`income:2026-09-30`与`cashflow:2025-09-30`失败。它不会抓新行情/财报，不补造旧版没有的TTM覆盖计数或恢复日志，也不证明第三方接口现在已恢复。

CI运行全部自动测试，并执行该真实历史只读回放、上传JSON/中文说明附件。故障注入测试另外验证定向补取、双层缓存刷新、历史桥接、未来公告、预算、损坏缓存、计数/状态篡改拒绝和直接发布拦截。

本次改动通过PR交付；合并并在正式扫描执行前，不能声称线上已经启用。上游接口仍可能持续不可用；该情况下应当得到清楚的异常诊断与已核验部分，而不是一份假装完整的榜单。
